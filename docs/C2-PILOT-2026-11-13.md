## What is built

Burnley and Blackburn with Darwen each have a standalone local page. The player
starts with the prior year's own Band D charge, changes that charge or selected
net service totals, and sees changes in financing, spending and the remaining
difference. Reset can restore the freeze or the published baseline. The latter
returns an exact zero. The published signed ledger remains separate and intact.

The current guessing game and fixed-total scenario are unchanged. The pilot
lives under `pilot/`, uses its own Astro configuration and builds only into
`.ops/c2-dist`. The production configuration, route list, sitemap, canonicals
and navigation do not include it. Both local pages are noindex. The pilot has no
analytics, no network requests for choices, no saved choices and no URL state.

The standard site's colours and fonts are reused. Desktop has a sticky result
panel; phones have a compact result strip while the controls are being used.
The reference ledger and starting calculation remain available without scripts.
The copy action includes the formula, input choices, edition, model version,
sources and source warnings. Clipboard failure exposes selectable text.

| Check | Burnley | Blackburn with Darwen |

| RA total council-tax requirement, GBP | 8,832,000 | 79,098,000 |
| Table 10 total requirement, GBP | 8,832,026 | 79,098,234 |

| Table 10 parish precepts, GBP | 222,800 | 198,234 |
| RA parish less Table 10, GBP | -800 | -234 |

RA prints integer thousands and Table 10 prints pounds. A difference within
half a printed thousand is compatible with that precision; it does not prove
rounding is the cause. Burnley's GBP 800 parish difference exceeds that screen.
No explanation has been established and neither source is adjusted. The page
and copied summary flag this review. **Burnley is not cleared for public C2
release.** It remains useful as an explicitly labelled local arithmetic pilot
whose parish financing stays fixed. Blackburn passes the component screen but
still needs product review and release approval.

The prior research compared total tax amounts but did not perform this raw
parish-component comparison. Do not describe all 280 candidates as ready.

## Exact calculation

Internally, one unit is GBP 0.0001, represented by BigInt. Own Band D is stored
in pence; the published tax base is stored in hundredths of a Band D equivalent.
Their product therefore retains all printed precision. Chosen service amounts
are accepted to pennies. No floating-point money accumulator is used.

```
financing change = (chosen own Band D - published current own Band D) * tax base
spending change = sum(chosen editable service totals - published service totals)
remaining difference = spending change - financing change
```

| Pilot | Freeze calculation, GBP before display rounding |
| --- | ---: |
| Burnley | (351.44 - 344.58) * 24,497 = 168,049.4200 |
| Blackburn with Darwen | (2,062.96 - 1,964.93) * 38,246.03 = 3,749,258.3209 |

The Blackburn result was independently checked using Python Decimal after a
mistyped expected test value was caught. The generated audit and model agree.
This is a current-tax-base sensitivity, not the actual yield of the year's tax
increase, a future forecast or a published budget deficit.

Money displays to pennies. A nonzero difference smaller than a penny is shown
as such, never labelled balanced. The copied summary preserves four decimals.
An implication for production: penny-only spending controls cannot always erase
a fractional-penny tax difference. Keep exact and displayed balance distinct.

Net-income groups and published zeros remain fixed. Education and public health
also remain fixed because restricted funding is not modelled. Grants, reserves,
all other financing, and the non-service adjustments between RA lines 799 and
900 stay fixed. No change represents an evidenced efficiency or service outcome.
The symmetric input range of zero to twice each positive published amount is a
prototype range, explicitly labelled as neither legal nor deliverable bounds.

RA returns, nine absent returns and seven note 4 discrepancies. That leaves
280 initial candidates with annual own-precept joins.

The new `docs/C2-COVERAGE-2026-11-13.json` applies the raw total and parish
component precision screens and flags authority-specific source notes. **178
of 296 pass this narrower arithmetic/component/notes screen.** Review reasons
overlap: 54 total-requirement differences exceed the screen, 29 parish components
need review, and 33 authorities have notes to review, in addition to the nine
missing and seven note 4 cases. These figures are review categories, not a claim
that official data is wrong. The 178 have not received national legal-category
mapping or a full authority-by-authority source review and are not a release
coverage promise. Counties remain outside this pilot.

## Run locally

Use the repository's Node 22 version and `npm ci`. Obtain the seven raw files
from the URLs recorded in the fixture if they are absent; the build checks every
hash and stops if any edition differs. It does not silently fetch an updated
edition or fall back to incomplete data.

```
npm run build:pilot
npm run preview:pilot
```

Open `http://127.0.0.1:44427/burnley/` or
`http://127.0.0.1:44427/blackburn-with-darwen/`. The normal `npm run build` still
builds the public site to `dist`. The pilot build script refuses CI and Pages
deployment environments. It uses the existing CSP hash writer with an explicit
output directory; default production behaviour is unchanged.

## Production build brief

1. **Resolve source gates first.** Review the raw component exceptions, starting
   with Burnley's GBP 800 parish difference. Resolve through attributable source
   evidence or leave the authority out. Missing returns and unresolved note 4
   authorities remain excluded. Preserve all source notes and printed precision.
2. **Map the selected release cohort.** Pin referendum rules by GSS and edition,
   including special categories and exceptions. Test both sides of every strict
   and inclusive boundary. Do not generalise the pilot's two categories to every
   council. County interaction requires a separate prior-precept join and review.
3. **Set a first release cohort from evidence.** Start with councils that pass
   every gate. A review-ready Blackburn page is a better first candidate than a
   promise of 280 pages. Regenerate a full eligibility manifest; failures must
   produce an honest unavailable explanation, never a national estimate.
4. **Finish the product interface.** Review the mobile control range, the
   fractional-penny state, source-warning placement and how the mode is entered
   alongside the existing game. Keep assumptions and the published baseline
   distinct. Add durable browser regression tests when the routes are agreed.
5. **Integrate only the reviewed mode.** Move reviewed components into the
   production route system, with the correct static-path, sitemap, source and
   distribution gates. Keep the current guessing and fixed-total modes intact.
   A whole-site number comparison must prove published amounts are unchanged.
6. **Release review.** Full unit, Astro, image, distribution, text, keyboard,
   accessibility, phone/desktop, both-theme and production-CSP checks. Review the
   exact final head and obtain Tom's explicit publication instruction.

Reserves controls, fees, demand shocks, jobs or care-place consequences,
achievable-savings claims and future-year carry remain separate research work.
They cannot be inferred from RA net service totals. No public launch date is
promised by this local session.
